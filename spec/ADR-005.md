# ADR-005 — Versionamento, Estabilidade e Distribuição

**Status:** Aceito  
**Data:** 2026-09-13  
**Decisores:** Lumen Lang Team  
**Relacionado a:** `SPEC.md` §8-9, todos os ADRs

---

## Contexto

Lumen está em `0.1.0-draft`. Precisamos de política de versionamento que:

- Permita quebrar sintaxe/tipos antes de 1.0 sem trauma.
- Dê confiança para early adopters (`stdlib` ainda instável).
- Coordene `spec` (markdown normativo), `compiler`, `stdlib`, `tools`.

Opções:

- (A) SemVer puro desde 0.1 → `0.1.0` quebra compat sem aviso; 1.0 estabiliza.
- (B) CalVer (`2026.09`) → bom para site, ruim para libs.
- (C) SemVer + draft + RFC + feature gates (escolhido).

Requisitos:

- `lumen --version` deve refletir spec.
- `Lumen.toml` (manifest) declara `lumen = "0.1"` compat.
- Breaking changes exigem ADR e minor bump.

---

## Decisão

### 1. SemVer com fase draft

```
0.1.0-draft → 0.1.0 → 0.2.0 → 1.0.0
 ^         ^      ^       ^
 |         |      |       +-- estável, compat garantida (SemVer strict)
 |         |      +---------- minor quebra compat (enquanto 0.x)
 |         +----------------- patch: bugfix, não quebra
 +--------------------------- draft: spec não congelada, pode quebrar sem bump
```

- Hoje: `0.1.0-draft` (spec em `spec/` é draft normativo, mas quebrável com ADR).
- Próximo: `0.1.0` (primeiro release congelado; `EBNF.md`/`TIPOS.md`/`SEMANTICA.md` estáveis para patch).
- `0.2.0` pode quebrar `0.1` (ex: mudar `match` syntax), mas exige ADR e `MIGRATION.md`.
- `1.0.0` quando `conformance` + `stdlib` + 3 backends estáveis.

### 2. Versionamento de spec vs implementação

- `spec/` tem `Versão: 0.1.0-draft` no topo de cada `.md`.
- `compiler` e `stdlib` têm `version = "0.1.0-draft"` em `Lumen.toml` / `Cargo.toml`.
- Compatibilidade: `lumen build` verifica `spec_version == compiler_version` major.minor; mismatch → erro com sugestão de upgrade.

### 3. Feature gates e RFC

- Features instáveis atrás de `#[feature(async_await)]` ou `#![feature(...)]` no topo do crate.
- Toda feature instável requer ADR draft + `#[feature]`; estabilização remove gate e bump minor.
- RFC leve: PR com template `docs/rfc/NNN-titulo.md`, 2 aprovações, vira ADR aceito.

### 4. Distribuição e toolchain

- `lumenup` (rustup-like) instala `lumen` + `std` + `wasm` target.
- `Lumen.toml`:

```toml
[package]
name = "hello"
version = "0.1.0"
lumen = "0.1"

[dependencies]
std = "0.1"
```

- `lumen pkg publish` verifica SemVer; `0.x` permite `^0.1` (compat minor).

### 5. Changelog e deprecation

- `CHANGELOG.md` com `Added/Changed/Fixed`.
- Deprecation: `#[deprecated("use X")]` por 1 minor antes de remoção (mesmo em 0.x).

---

## Consequências

**Positivas:**

- Early adopters sabem que `0.1.0-draft` pode quebrar, mas com ADR documentado.
- SemVer estrito após 1.0 dá confiança para produção.
- Feature gates permitem experimentar `async`/`macros` sem congelar.

**Negativas:**

- `0.x` quebra frequente pode frustrar; mitigado por `MIGRATION.md` e `lumen fix --edition 0.2`.
- Manter spec version sync com code version exige CI check.

**CI:**

- `infra/ci` roda `spec-version-check`: `grep Versão spec/*.md == version Lumen.toml`.
- `conformance/` taggeado por spec version.

---

## Exemplo

```
spec/EBNF.md       → Versão: 0.1.0-draft
spec/TIPOS.md      → Versão: 0.1.0-draft
Lumen.toml         → version = "0.1.0-draft"
lumen --version    → lumen 0.1.0-draft (spec 0.1.0-draft, backend c/wasm/vm)
```

Upgrade `0.1.0-draft` → `0.1.0` congela sintaxe; `0.2.0` pode adicionar `where` novo com RFC.
