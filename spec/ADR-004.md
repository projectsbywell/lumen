# ADR-004 — Targets de Compilação: C, WASM e VM

**Status:** Aceito  
**Data:** 2026-09-13  
**Decisores:** Lumen Lang Team  
**Relacionado a:** `SPEC.md` §8, `SEMANTICA.md` §2/4, `EBNF.md` §12

---

## Contexto

Lumen promete "write once, run everywhere": CLI nativo performático, web via WASM, e REPL/testes rápidos.

Opções de backend:

- **(A) LLVM only:** ótimo nativo, mas build pesado, sem WASM direto, sem VM interpretada.
- **(B) Bytecode VM only:** portável, mas não nativo performático.
- **(C) Multi-backend com HIR/MIR comum (escolhido):** `frontend` → `middle` → `backend/{c,wasm,vm}` compartilhando semântica única (`SEMANTICA.md`).

Requisitos:

- `lumen build --target native` → binário sem dependência LLVM instalada (usar `cc`).
- `lumen build --target wasm` → `wasm32-unknown-unknown` rodando no browser/Node.
- `lumen test` / `lumen run` → VM interpretada com startup <50ms.
- Semântica observável idêntica entre targets (exceto overflow e tempo).

---

## Decisão

### 1. Pipeline

```
source.lm
  → frontend (lexer/parser EBNF.md → AST → HIR)
  → middle (typeck TIPOS.md, borrowck ADR-003, monomorfização, MIR)
  → backend
     ├─ c    : MIR → C99 → cc/clang → binário nativo
     ├─ wasm : MIR → WASM (via wasm-encoder) → .wasm
     └─ vm   : MIR → bytecode → interpreter (Rust/Go host)
```

`middle` é comum e garante soundness; backends são lowering.

### 2. Backend C (native)

- Gera `out.c` com structs C para `Ponto`, enum como `tagged union`, `string` como `{char* ptr, size_t len}` com refcount ou arena (escolha: arena por função + `Drop` explícito).
- Overflow: `debug` → `panic` (abort), `release` → wrap (C wrap). Documentado em `SPEC.md`.
- Async: lowering para state machine C com `switch` + epoll/kqueue (futuro: `libuv`).
- Vantagem: sem LLVM, `cc` sempre disponível, debug fácil (`out.c` legível).

### 3. Backend WASM

- Mesma MIR, mapeia `int`→`i64`, `float`→`f64`, `string`→ WASM linear memory com allocator `wee_alloc`.
- Async mapeia para `Promise`: `await` vira `await` JS interop quando import `std.http` usa `fetch`.
- `println` → `console.log` ou `wasi stdout`.

### 4. Backend VM

- Bytecode stack-based, instruções: `LOAD, STORE, ADD, CALL, MATCH, BORROW, AWAIT, YIELD`.
- `Future` interpretado como coroutine com `Poll`.
- Sem monomorfização completa: dict-passing para genéricos (menor size, mais lento, idêntico semanticamente).
- Usado por `lumen test` para descobrir `#[test]` via reflexão do bytecode.

### 5. Semântica única, diferenças documentadas

| Aspecto | native (C) | wasm | vm |
|---------|------------|------|-----|
| `int` overflow | panic debug / wrap release | wrap | panic debug / wrap release |
| `float` NaN | IEEE754 | IEEE754 | IEEE754 |
| `async` scheduler | epoll | Promise | cooperative single-thread |
| `panic` | abort + core | trap | exception com stack trace |
| performance | melhor | bom | interpretado |

Conformidade: todos passam `conformance/` com mesmo output (exceto tempo/stack trace).

## Consequências

**Positivas:**

- Sem LLVM dependency → onboarding simples (`apt install clang` basta).
- `out.c` auditável; `wasm` roda no browser sem transpile JS.
- `vm` dá REPL instantâneo e `lumen test` rápido.

**Negativas:**

- Backend C gera C verboso; otimizações limitadas vs LLVM -O2 (mitigado por `clang -O2` no C gerado).
- Três backends → 3× manutenção; mitigado por MIR comum (maior parte da lógica em `middle`).
- WASM GC proposal ainda não usado; `string` manual memory.

**Roadmap:**

- v0.2: substituir backend C por LLVM opcional (`--target native-llvm`) mantendo C como fallback.
- v0.3: WASM GC para structs sem linear memory hacks.

## Exemplo

```bash
# nativo
lumen build --target native -o hello
./hello  # chama cc internamente

# wasm
lumen build --target wasm -o hello.wasm
node -e "import('./hello.wasm')"

# vm
lumen test              # usa vm, descobre #[test]
lumen run hello.lm      # vm interpretado
```

Mesmo `hello.lm`:

```lumen
module hello
import std.io
pub fn main() -> int { io.println("olá"); return 0; }
```

roda idêntico nos três.
